# Restic REST Backend + Authelia Auth — Research

**Status**: Decision record. Implementation tracked in `_plans/RESTIC_OFFSITE_BACKUP.md`.
**Trigger**: Reinstall-readiness audit (2026-09-14) found `home-backup`'s restic repository
defaults to `$HOME/.local/share/backups/home-backup` — same disk as the data it protects.
`.chezmoidata/globals.yaml` says so explicitly: *"Repository stored locally (no remote sync
by default)."* A full disk wipe destroys the backup along with the data.

---

## 1. Backend choice: restic REST server

Restic supports several remote backends natively: local/SFTP, its own REST protocol
(`rest:`), S3-compatible object storage, rclone-wrapped backends.

| Option | Verdict | Why |
|---|---|---|
| SFTP | Rejected | Zero-install if SSH already runs, but no tamper protection — a compromised or buggy client can delete/overwrite old snapshots. |
| **`rest-server`** | **Chosen** | Restic's own purpose-built server. Single static Go binary. `--append-only` mode: client can push new snapshots but cannot delete or overwrite existing ones — real protection given the backup set includes `.ssh`, `.keys`, `.gnupg`. |
| MinIO / S3 | Rejected | Heavier (own auth, buckets, erasure coding) for capability not needed here — disk redundancy is already handled at the BTRFS layer (`_guides/MULTI_DEVICE_BTRFS_SETUP.md`). |

`rest-server` runs with `--no-auth` in this design — auth is delegated entirely to the
reverse proxy / Authelia layer (see §2), so rest-server carries no credential of its own.

---

## 2. Auth layer: SWAG (nginx) + Authelia

Home lab already runs SWAG (linuxserver.io nginx+certbot bundle) and Authelia. Reusing
that identity layer beats standing up new auth machinery — but restic is a **non-browser**
client, and that matters.

### 2.1 The gotcha

SWAG's stock `authelia-location.conf` calls `auth_request /authelia/api/verify` (or, on
newer Authelia, `/api/authz/auth-request`) — the **browser** endpoint. On auth failure it
302-redirects to Authelia's login portal HTML page. A non-interactive backup cron job
doesn't get a login prompt to fail on — it gets redirected into an HTML page and errors out
confused, every run.

### 2.2 The fix: dedicated basic-auth authz endpoint

Authelia (4.38+) supports naming multiple `authz` endpoints in `configuration.yml`, each
with its own implementation and auth strategy. A second endpoint using the
`HeaderAuthorization` strategy validates a plain `Authorization: Basic <user:pass>` header
against Authelia's user database with no session/cookie/redirect involved, and answers with
a direct `401` instead of a redirect:

```yaml
server:
  endpoints:
    authz:
      auth-request:
        implementation: 'AuthRequest'        # existing — browser apps, unchanged
      auth-request/basic:
        implementation: 'AuthRequest'
        authn_strategies:
          - name: 'HeaderAuthorization'
```

Nginx side needs a **second, separate** location/authrequest snippet pair
(`authelia-server-basic.conf` / `authelia-location-basic.conf`) pointed at
`/api/authz/auth-request/basic`, returning bare `401` on failure instead of following
`$upstream_http_location` into a redirect. The existing browser snippets stay untouched —
other services keep working exactly as before.

Access control: a dedicated rule scoped to just the restic subdomain, `policy: one_factor`.
2FA is deliberately out of scope for this credential — there's no way for a headless cron
job to supply a TOTP code. The compensating control is a long random password treated like
any other repo secret, plus keeping the endpoint off the public internet (Tailscale/WireGuard
only, not port-forwarded).

Source: Authelia's official NGINX integration guide confirms this exact dual-endpoint
pattern (`/api/authz/auth-request` vs `/api/authz/auth-request/basic`) as the current
(4.38+) recommended approach for mixed browser/non-browser protection —
<https://www.authelia.com/integration/proxies/nginx/>.

### 2.3 Service account

New Authelia user (`users_database.yml`), not a reuse of the personal login — same
principle as not reusing SSH keys across services elsewhere in this repo.

## 3. Credential storage: keyring over flat file

Two credentials are in play, with different treatment:

| Credential | Scope | Storage |
|---|---|---|
| Restic repo encryption password | Local, per-machine, generated by `home-backup init` today | Flat file `~/.local/share/backups/.restic-password`, `chmod 600`, never chezmoi-tracked. Already the repo's existing convention — kept as-is. |
| Authelia Basic-Auth credential (new) | Network-facing, gates access to the remote repo | **`gnome-keyring` via `secret-tool`**, not a flat file. |

Why the credential-storage split: the repo password never crosses a network boundary and
was already outside git — no upgrade needed. The Authelia credential is new and
network-facing, so it gets the stronger treatment available: `gnome-keyring` is already a
hard dependency in this repo (`run_once_before_001`, section 10 — WiFi credential storage),
so reusing it costs one package (`libsecret`, for the `secret-tool` CLI) instead of standing
up a new secret-management mechanism. Encrypted at rest, unlocked automatically at session
login, never written to disk in plaintext, never chezmoi/git-tracked.

Rejected: age-encrypted-and-committed (`private_dot_keys/encrypted_private_*.age`, the
pattern used for API keys). That pattern exists for secrets that must be portable across
machines via git + Vaultwarden. This credential is currently single-machine and doesn't need
that distribution mechanism — revisit if a second machine needs to back up to the same
`rest-server`.

## 4. Side finding: `executable_home-backup` assumes a local path

`REPO` is used as a filesystem path in five places (`[[ -d "$REPO" ]]` ×3,
`mkdir -p "$REPO"` ×2) and would silently misbehave once `REPO` becomes a `rest:` URL —
`[[ -d "rest:https://..." ]]` is simply false, so `_check_initialized` would always report
"not initialized" even against a live repo. Not optional to skip; tracked as phase 1 work in
the implementation plan.
