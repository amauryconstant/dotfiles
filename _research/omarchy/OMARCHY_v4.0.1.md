# Omarchy v4.0.1 — Release Research

**Date researched**: 2026-08-30
**Previous version**: v4.0.0-beta3 (empty intermediate tag, 0 commits; effective baseline is v4.0.0)
**Commits**: 112
**Source**: Commit log fallback

---

## Summary

A patch/security release for the v4.0.0 "Quattro" shell rewrite (see `OMARCHY_v4.0.0.md` for the shell/Quickshell architecture; not re-documented here). Almost all 112 commits are backports of fixes merged to the `quattro` branch after v4.0.0 shipped, applied onto the v4.0.x release branch. Four commits are explicitly security-tagged (FIDO2 authfile symlink/ownership flaw, USB/monitor device names executed as Hyprland Lua, an installed theme running arbitrary code at login/startup, and a video title forging the Download Video play command), plus several more security-adjacent hardening commits (privileged DNS helper PATH pinning, git-transport-helper guards on theme/plugin install, removal of an unused root-shell command with unsanitized `$USER` interpolation) and one default-behavior change (Docker group membership is no longer granted automatically).

## Breaking Changes

- **Sudoless Docker no longer granted by default**: previously, install/first-boot provisioning added the user to the `docker` group automatically, which is root-equivalent (`docker run -v /:/host` rewrites the host as root, no password). v4.0.1 stops granting the group on install, first-boot, and Quattro upgrade; a migration removes it from existing installs. Docker TUI and the Windows VM now reach the daemon through a polkit prompt; the plain `docker` CLI runs under `sudo`. Re-enabling is an explicit, warned opt-in under `Setup > Security` (toggling it now offers a reboot, since group membership is fixed at login). Omarchy path: `bin/omarchy-remove-security-sudoless-docker`, `applications/Docker.desktop`, `bin/omarchy-launch-docker-tui`
- **`omarchy-sudo-reset` command removed**: unused by anything in the repo, and interpolated an environment-supplied `$USER` unsanitized into `su -c "faillock --reset --user $USER"`. `omarchy sudo reset` now falls through to the router's unknown-command path. Existing PAM lockout behavior (`deny=10 unlock_time=120`, self-clearing after 2 minutes) is unaffected; the documented root-TTY reset in the troubleshooting manual still works.
- **User themes installed via `omarchy theme install <url>` no longer ship executable code**: staging now copies only `colors.toml`, `light.mode`, preview/unlock images, and `backgrounds/*`; `*.lua` (Hyprland/Neovim config), the four terminal configs, and `vscode.json` are dropped and generated instead from `default/themed/*.tpl`. Per-theme overrides of these generated files are no longer available to third-party ("extra") themes — only first-party themes under `$OMARCHY_PATH/themes` and themes the user wrote themselves are unaffected. Existing installs are re-staged once via `omarchy-theme-refresh`.

## Bug Fixes

- **[Security] FIDO2 authfile predictable `/tmp` path**: `omarchy-setup-security-fido2` staged the pamu2fcfg output at `/tmp/fido2` and moved it into place with `sudo mv`; any local user could pre-create `/tmp/fido2` as a symlink, and `rename(2)` doesn't dereference the final component, so the privileged move installed the attacker's target as pam_u2f's global authfile (consulted by `sudo` and `polkit-1`). It also carried the staged file's ownership into `/etc`, so every prior install left `/etc/fido2/fido2` owned by the invoking (non-root) user — no attacker needed, any process running as that uid could append its own credential and pass the sudo prompt. Fixed by staging as root beside the final authfile, piping pamu2fcfg output directly, publishing with atomic `mv -Tf`, rejecting non-regular authfile states, and installing `root:root 0644`; a migration repairs prior installs by replacing the inode. Omarchy path: `bin/omarchy-setup-security-fido2`, `bin/omarchy-remove-security-fido2`, `migrations/1787494718.sh`
- **[Security] USB/monitor device names executed as Hyprland Lua**: input-device and monitor names come from USB descriptors / `hyprctl` output (attacker-influenceable), but the touchpad/touchscreen toggle and monitor scripts interpolated them directly into `hyprctl eval` and into generated `.lua` files Hyprland re-executes on reload. `XF86TouchpadToggle` is bound `locked = true`, so a malicious device name could execute Lua from the lock screen as the logged-in user, and a persisted disable ran on every subsequent boot. Publicly reported by Jorrit Jongma / Chainfire. Fixed: the disabled-device name is now stored as plain-text data in a `*-disabled-name` sidecar, read back by `default/hypr/disabled-input-device.lua`; live `hyprctl eval` Lua-quotes the name and rejects control characters; all four monitor scripts validate output names against `^[A-Za-z0-9._-]+$` before writing them as Lua. A migration sanitizes leftover legacy `*-disabled.lua` files. Omarchy path: `bin/omarchy-toggle-input-device`, `bin/omarchy-hyprland-monitor-clamshell`, `bin/omarchy-hyprland-monitor-internal`, `bin/omarchy-hyprland-monitor-internal-mirror`, `bin/omarchy-hyprland-monitor-scaling`
- **Stop an installed theme from running code**: covered under Breaking Changes above (staging filter). Additional hardening in the same PR: `omarchy theme install`/`remove`/`set` now pass URLs/names with `--` so a leading-dash value can't be read as a git/basename option, reject `<helper>::<address>` git transport-helper URLs (`ext::`, etc.) while still allowing scp-style IPv6 hosts (`git@[2001:db8::1]:org/repo.git`), and reject empty/`.`-prefixed/`/`-containing theme names before they reach an `rm -rf` path. `omarchy-plymouth-set-by-theme` no longer follows a symlinked `unlock.png` when republishing it to `/usr/share`. Omarchy path: `bin/omarchy-theme-install`, `bin/omarchy-theme-remove`, `bin/omarchy-theme-set`, `bin/omarchy-plymouth-set-by-theme`
- **[Security] Video title forging the Download Video play command**: the host parsed yt-dlp's `after_move` output as title+path; a newline in page metadata could forge the path, and clicking the resulting toast handed that forged value to `mpv` as options. Fixed to print only the real downloaded file, reject anything outside the download directory, invoke `mpv` with `--`, read `realpath`'s NUL-terminated output (preserving a trailing-newline filename) rather than command substitution (which stripped it), and refuse a resolved path containing control characters. Omarchy path: `bin/omarchy-download-video` (or equivalent yt-dlp wrapper)
- **Guard `omarchy plugin-add` against git transport-helper URLs**: `omarchy-plugin-add` cloned a user-supplied git URL without the transport-helper guard added to `omarchy-theme-install` in the same release; closes the gap for the sibling command (defense in depth — stock systems set no `protocol.*` override, so git's own `protocol.ext.allow=never` default already blocked exploitation). Omarchy path: `bin/omarchy-plugin-add`
- **Pin trusted PATH in privileged DNS helper**: `omarchy-dns` runs as root via a passwordless sudoers grant (`etc/sudoers.d/omarchy-dns`) and resolved bare helpers (`dirname`, `install`, `tee`, `rm`, `nmcli`, `systemctl`, `awk`) through the caller's `PATH`/sudo `secure_path`. A `dev link` setup (`omarchy dev link`) prepends a user-writable checkout's `bin/` to `secure_path`, so write access to a dev checkout became arbitrary root execution with no password prompt. Fixed by pinning `PATH=/usr/local/sbin:/usr/local/bin:/usr/bin:/usr/sbin:/bin:/sbin` once `EUID == 0`; the unprivileged wrapper phase keeps the caller's `PATH` so it can still find `sudo`/`pkexec`. Omarchy path: `bin/omarchy-dns`
- **Fall back to polkit / password-free DNS provider switching**: `omarchy-dns` falls back to polkit when the DNS sudoers grant is missing, and switches DNS providers without a password prompt.
- **Notification click actions run as safe argv** instead of shell-interpolated strings, closing an injection path for a malicious notification's click action.
- **`psmouse` quirk failing every install**: `install/hardware/fix-synaptic-touchpad.sh` called `modprobe` against the running kernel via `uname -r`, but during the ISO finalizer (inside `arch-chroot`) that names the live ISO's kernel while `/lib/modules` holds the target's — the two never match on a non-T2-Mac install, so `modprobe` exited 1 and, under `set -euo pipefail`, aborted every fresh install with a touchpad named "synaptics" (reported from a ThinkPad). Fixed to probe with `modprobe -qn` first and warn instead of failing when the module can't be resolved for other reasons.
- **`Clone Plugin` failing with "unknown clone option"**, race conditions in notification popup/history handling, `o.shell_succeeds()` always returning false inside Hyprland, Windows VM RDP window never opening, `foot.ini` configs holding a literal `\n[text-bindings]` line, mise wrappers writing to stdout, passwordless OWE Wi-Fi handling, UTF-16 and mixed UTF-16 clipboard text decoding, webp decoding in the shell, speed-test dial locale formatting, calendar day names forced to English, bar sticking in move mode after a press-and-hold, closed network panels leaving Wi-Fi scanning enabled, Bluetooth discovery not stopping on panel close, and an auto-scaled internal panel being left alone in clamshell recovery.

## Improvements

- **Reboot flag on Docker group changes**: toggling sudoless Docker (grant or revoke) now flags that a reboot is needed, since group membership is fixed at login; the Setup > Security menu shows only the relevant entry (grant vs. revoke) rather than both.
- **`omarchy update`**: `Extra Themes` is only offered when at least one extra theme is actually installed.
- **Wait for keypress locally** instead of asking `gum` to, in interactive prompts.
- **README manual TOC renumbered** after the Extra Themes chapter was dropped (extra themes now point to the omarchy.org page / PRs to omarchy-site instead of being bundled).
- **Taildrop**: a received file now waits to be answered instead of auto-accepting/rejecting.
- **Package cache pruned before updating.**
- **Switched to the packaged `quickshell`** now that upstream 0.3.1 shuts down synchronously (was previously a workaround/patched build).
- **Switched to the `mise-bin` package.**
- **Claude/Codex agents launched with auto-review** instead of full bypass mode.

## Configuration Changes

- **Docker group state removed from install/first-boot provisioning templates**: no automatic path re-grants the `docker` group; a migration (reusing `omarchy-remove-security-sudoless-docker`) removes it from existing installs so the change and its user-facing notice share one source of truth. Windows VM's Docker Compose config moves to a root-owned directory writable only by an elevated, input-validated writer; VM volume paths are rebuilt from `$HOME` on migration rather than trusted from the legacy user-writable file; the guest password moves from a world-readable compose file to a private `0600` per-user file.
- **Theme staging filter (`omarchy-theme-set`)**: for themes with a `.git` directory or symlink under `~/.config/omarchy/themes` (i.e., installed via `omarchy theme install`, not user-authored), only `colors.toml`, `light.mode`, preview/unlock images, and `backgrounds/*` are copied into the staged theme; `*.lua`, the four terminal configs (`alacritty.toml`, `kitty.conf`, `foot.ini`, `ghostty.conf`), and `vscode.json` are dropped and generated from `default/themed/*.tpl` instead. `btop.theme`, `chromium.theme`, `helix.toml`, `icons.theme`, `keyboard.rgb`, and `shell.toml` remain theme-controlled (not code-carrying). Omarchy path: `bin/omarchy-theme-set`, `default/themed/*.tpl`
